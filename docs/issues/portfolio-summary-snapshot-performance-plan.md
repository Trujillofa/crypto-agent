# Portfolio summary: snapshot and contention decision gate

Status: investigation only; no implementation, no database or live trading access. Base: crypto-agent `a1f7c66915131240a6f9840568555e4f7555416a` (remote main checked). Do not loosen `_db_lock` or ship a query rewrite until the snapshot decision and gates below are satisfied.

## Observed call graph and invariants

- `src/main.py` creates a `PortfolioManager` and shares it with executors and the overseer. `OverseerAgent._cmd_status` and `_build_context` call `get_portfolio_summary`; `collect_agent_report` creates a separate manager, calls daily/campaign reads and then summary; `scripts/smoke_test.py` also calls it. The report's separate reads and `_build_context`'s subsequent in-memory positions are not one atomic snapshot with the summary.
- `get_portfolio_summary` (`src/portfolio/manager.py:476-528`) holds an **instance-local** lock through pool acquisition and eight sequential `fetchval`s; open, close, partial reduce and quantity update take that same lock and hold it over DB work and local state updates. Several other stats methods share it too. Do not weaken their ordering with a summary without an explicit replacement contract and tests. Startup `_ensure_schema`/`_normalize_open_positions`, a different manager/process, and direct SQL writers do not share this lock. Open/close/reduce update positions and insert a trade in one transaction; summary itself starts no explicit transaction. Pool creation does not set an isolation level: under PostgreSQL's usual READ COMMITTED default, each summary statement has a separate snapshot. Database/server settings must be checked in a disposable fixture, not assumed for production.
- Summary counts all statuses for total, only `'open'`/`'closed'` for their counts, and only closed positions for PnL and wins/losses. PnL is `DOUBLE PRECISION`, `SUM` ignores NULL and falls back to zero; zero and NULL are neither wins nor losses. Trades are independently scoped by normalized agent ID, MAX(time) is NULL when absent, unrealized is 0.0. Floating SUM order can change with query plans/parallelism; numerical equivalence must be specified and exercised, not assumed bit-exact.
- The existing test (`tests/test_portfolio_manager.py:229`) supplies sequential mock return values: it does not run SQL, exercise isolation, establish atomicity, or cover concurrent writers. Existing method can report a combination that never existed at one instant if a separate connection commits between scalar queries. A single combined statement would provide one PostgreSQL statement snapshot; that **eliminates** possible old outcomes and changes the cross-connection observation contract. It is potentially an improvement, not a proven behavior-preserving rewrite. Clarify/approve the desired contract before implementing.

## Decision and executable acceptance gates

1. **Decide the contract first.** Have an owner explicitly approve whether cross-connection summary fields must share one statement snapshot and that previously possible mixed-read observations may disappear. State how consistency with in-memory positions, separately collected risk and daily/campaign figures is scoped; do not claim they form one atomic report. If exact current possible observations must remain, stop: batching the eight statements into one snapshot does not meet that contract. No unsafe lock removal as a substitute.
2. **Prototype only after approval.** Keep the same instance lock around pool acquisition and the SQL, maintaining ordering with same-manager mutations. Consider a *single* parameterized SQL statement with separate aggregate subqueries for positions and trades; avoid joins that multiply rows. Scope each to the normalized `$1` agent. Preserve status filters, coalesce/NULL, timestamp and return types. Avoid implicit ordering claims. No cache, mutation, schema/index or config changes in this optimization.
3. **Run against disposable, synthetic PostgreSQL**, using a scratch-only isolated server and private Unix socket, no production credentials, mount, containers, ports, or data. Reproduce actual table DDL and relevant indexes from the repository and document server version, isolation and schema. Exercise the actual `PortfolioManager` method via an injected pool, not a handwritten Python approximation. A separate baseline checkout and candidate checkout must use identical fixtures and clocks. Test empty tables, other agent and NULL agent rows, mixed statuses, no trades, multiple trade timestamps, NULL/zero/negative/positive PnL, partial reductions, and double-precision edge values. Check every dataclass field, explicit acceptable floating tolerance (or exactness if owner requires it), NaN/infinity policy if admissible, and win-rate behavior.
4. **Deterministic concurrency tests:** coordinate connections with events/barriers, not sleeps. For baseline, pause after an early query, commit an atomic external open or close plus trade, resume, and assert the demonstrable mixed result. For candidate, coordinate an external commit before and after the combined statement snapshot and assert the entire answer is the pre- or post-commit state, never mixed; check all fields. Also force same-manager open, close, reduce and quantity update to contend while summary is paused, and the inverse ordering; verify DB plus memory and lock release on exception/cancellation and pool acquisition cancellation. Include separate managers and a direct external transaction to demonstrate the lock's scope. Test uncommitted then rolled-back writes are invisible. Document if SQL scheduling makes the snapshot barrier require a test-only SQL function/advisory coordination; ensure the test actually pauses *after* snapshot establishment.
5. **Benchmark before/after** on equal synthetic seed, schema, indexes, hardware, DB/pool settings and workload: same-manager writer lock wait and whole summary p50/p95/p99, actual query count and round trips, both idle and concurrent workloads, warmup and repeated samples; use representative row counts/distributions and `EXPLAIN (ANALYZE, BUFFERS)` on synthetic fixtures. Rework the fake benchmark to support the candidate's actual API and preserve 8-vs-1 query verification; label fake delay separately from PostgreSQL timings. State sample size/variance and reject a change if contention improvement is not repeatable or query-plan/large-data regression is material. Do not present a fake latency reduction as measured production benefit.
6. **Validation and delivery:** no implementation PR until contract is accepted, deterministic SQL/concurrency tests and full suite pass (report pre-existing/isolated-network failures honestly), benchmark comparison is reproducible, current main is rechecked and an independent review is complete. Inspect all PR-trigger workflows and invoked scripts plus configured automation before pushing; push a draft only if side effects are acceptable. No deployment, trade, live DB, config change or release control is authorized by this plan.
